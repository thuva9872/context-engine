# ADR 0016: Structured-data graph nodes via RML

**Status:** Proposed

**Date:** 2026-10-05

## Context

Connectors already deliver structured records: Salesforce rows and database rows arrive as `application/json`, and a source may deliver CSV or XML files. Until now every record took one path — the worker extracted its text and the knowledge provider chunked it and ran its own language-model extraction to find entities and relationships (ADR 0001, ADR 0015). For prose that is the only option, but for a structured record it throws away structure the connector already has: fields, keys, and foreign keys that name relationships exactly. Re-discovering them from flattened text is slower, costs a model call per record, and is only as reliable as the model.

RML (RDF Mapping Language) is the standard way to turn relational and tree-shaped data into RDF. A mapping written once for a schema turns each record into subjects, typed properties, and foreign-key edges deterministically, with no model in the loop. A proof of concept established the shape: introspect a schema, express it as an RML mapping in Turtle, let morph-kgc materialize the record to RDF, and translate that RDF into the provider's typed nodes and edges. The question this ADR settles is how that path lives inside the engine without weakening the guarantees the text path already gives — pinned ids, per-partition isolation, and crash-safe replace and delete (ADR 0007).

A mapping is schema-specific: it names the columns, keys, and foreign keys of one schema, so it is correct only where every record it applies to shares that schema. This fixes the scope. A structured mapping belongs on a **schema-homogeneous** source — a database table, a Salesforce object — where one source means one schema. It does not fit a **multi-modal** source such as Google Drive or file upload, whose files carry unrelated schemas even within one content type (one folder's CSVs have nothing in common): there is no single "mapping for CSV" to write. Those sources register no mapping and their records take the text path, which is the right path for heterogeneous content. The content type selects the parser, not the schema, so it never stands in for one.

## Decision

A source may carry an RML mapping per content type; a record whose content type has one becomes graph nodes and edges through that mapping instead of indexed text.

- **The mapping travels in source registration, keyed by content type.** `POST /v1/spaces/{spaceId}/sources` accepts `structuredMapping`, a JSON object from content type to Turtle, stored on the source. The key is the content type rather than a bare string because the worker must know which content type a mapping applies to — to pick the morph-kgc formulation (JSONPath for JSON, XPath for XML, tabular for CSV) and to decide whether a record is structured at all — so the stored value is inherently a (content type, mapping) association, not a lone document. A homogeneous source normally has exactly one entry; the map only matters in the rare case of a single source that emits more than one structured type. A source with no mapping behaves exactly as before. The mapping can be replaced later through the source-update route, like the audience mapping, wholesale; already-indexed records are not re-materialized until their next version arrives, so a corrected mapping takes hold as content flows, not retroactively.
- **The worker branches per record on content type.** After it reads and hash-verifies the staged bytes, the worker asks the source for a mapping for that record's content type. With one, it materializes; without, it extracts text. The branch is the only new decision in the write path; everything downstream of it is shared.
- **Materialization is provider-neutral; the RDF-to-node translation is private to the provider.** `ingestion/structured.py` runs morph-kgc over the staged bytes and the mapping and returns an `rdflib.Graph`, a W3C artifact that carries no provider concept. The translation from that graph to native `Entity`, `EntityType`, `DocumentChunk`, and `TextDocument` values lives under `knowledge_backend/providers`, so no provider type crosses the boundary (ADR 0001).
- **Node ids are deterministic and partition-namespaced.** A node's id is `uuid5(binding + subject IRI)`. Determinism makes a foreign-key template resolve onto its target node with no lookup, because the mapping writes the referencing IRI to equal the referenced row's subject IRI. Namespacing by the partition's native binding keeps the same source IRI from colliding across two partitions' datasets.
- **One record is one owned item, so reconciliation is unchanged.** The record is registered as a native content item under the same pinned id the text path uses, and every node, edge, and chunk it produces is stamped with that item's dataset and data id. The engine still tracks one backend reference per record; replace writes the new version and forgets the old id, and delete forgets the id, reclaiming exactly this record's graph. No language model runs on this path.
- **One document per record carries the record's id.** All of a record's chunks belong to a single `TextDocument` whose id is the record's native item id, so retrieval attributes those chunks back to the record and the engine resolves each piece of evidence to its source.

## Alternatives

- **Model-proposed mappings generated and cached in the engine:** rejected for now. It was the proof of concept's approach, but it puts a language model and a schema-introspection step inside the control plane. Letting the mapping arrive at registration keeps the engine deterministic and leaves mapping authorship — by hand or by a model — to the client.
- **Direct `db_url` materialization of whole tables:** rejected. It is the most faithful to RML's relational roots, but it would have the engine connect to source databases and break the staged-content, per-record model the whole pipeline rests on (ADR 0012). Database rows reach the engine as JSON records instead, and the mapping expresses their foreign keys as edges.
- **A single mapping string instead of a map:** rejected, though nearly equivalent. A bare string still cannot stand alone — the worker needs the content type beside it to pick the parser and to branch — so the honest minimum is a (content type, mapping) pair, which the map already is, degraded to one entry. Collapsing to a pair or two columns removes nothing and costs a migration, while giving up the rare multi-type case for free.
- **Writing nodes globally without an owning context (the proof of concept):** rejected. It produces a graph but stamps no ownership, so a later delete cannot find the record's nodes. Passing the dataset and item context is what lets the existing forget path reclaim them.

## Consequences

- The knowledge-provider extra gains `morph-kgc` and `rdflib`; both load only when the provider is enabled, and the engine still imports without them.
- CSV and XML join the upload allowlist so structured files can be staged at all; an unmapped record of those types still fails text extraction as before.
- Incomplete data is never lost. A record missing some fields its mapping names still materializes — the subject is built and the present fields become properties, the absent ones are simply skipped — so a sparse record yields a smaller node, not a failure. A record that materializes to *no* triples (it lacks the field the subject is keyed on, or the mapping does not match its shape) or whose materialization errors falls through to the ordinary text path instead of failing, so it is still indexed and searchable rather than dropped or left as an unretrievable empty node. The fallback is logged per record (`structured_materialization_fell_back` with the reason), so a mapping that fails for every record is visible rather than silent. On the fallback, a content type the text path cannot parse (CSV, XML) is read as plain text so nothing is dropped.
- A mapping's Turtle is parsed at registration and a malformed one is refused with a 400, so an authoring mistake is caught at the source rather than on every record. This is a syntax gate only: whether a well-formed mapping actually materializes a record — the right iterator, templates that name fields the data has — is decided by morph-kgc against real bytes at ingest, where a record that cannot be materialized fails terminally with a stable code like any other content the worker cannot index. The registration check is best-effort: a control plane built without the provider extra skips it and leaves the ingest-time check as the gate, so the control plane keeps no hard RDF dependency.
- Edge-relationship embeddings re-indexed under the deterministic node ids are not reclaimed when a record is replaced and then deleted. The graph nodes and the chunk vectors retrieval reads are reclaimed, and the deleted record holds no reference, so these stale embeddings are never returned as evidence. This is a recorded retention gap of the same class as the query-history gap in ADR 0007, not a leak.

## Validation

- `engine/tests/test_structured_rml.py` checks that materialization over a Salesforce-shaped fixture yields the expected subjects, that a broken mapping and an unsupported content type fail with stable codes, and that the adapter builds the expected nodes and edges with deterministic, partition-namespaced ids and a foreign-key edge that lands on its target.
- `engine/tests/test_live_cognee_provider.py` ingests a structured record end to end, answers a relationship question through the graph the mapping built, replaces the record and confirms the prior version's nodes are gone, and deletes it and confirms the graph and the chunk-retrieval path hold nothing of it — leaving only the recorded edge-embedding retention gap.
- `engine/tests/test_sources_api.py` registers a source with a well-formed mapping and rejects both an unsupported content type and malformed Turtle with a 400.
- The existing `engine/tests/test_record_indexer.py` and the full suite confirm the text path is unchanged when a source carries no mapping.
